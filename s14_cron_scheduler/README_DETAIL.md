# s14 通俗详解：没人再说话，Agent 怎么知道到点该工作了？

这份文档重新解释本章的 [README](README.md)，以当前带中文注释、使用 OpenAI 兼容接口的 [code.py](code.py) 为准。原 README 保留；本文已同步代码中的函数拆分与初始化方式。

不需要先理解 cron、调度器、生产者、消费者这些名字。我们从一个具体需求开始：

> 我现在告诉 Agent：“以后每天早上 9 点检查项目的测试结果。”之后我不再输入任何消息。

本章要补上的，就是“以后到点时，谁来发起这件事”。

阅读提示：先读第 1 到 5 节，把整个过程串起来；再读锁、时间表达式和保存机制。最后的限制是为了区分“教学代码已经做到了什么”和“实际系统还需要补什么”，不用一次记住。

## 1. 为什么有了 s13，还需要 s14？

### s13 解决的是：工作已经开始，但它太慢了

假设你说：“运行测试，顺便看一下配置文件。”

测试需要 30 秒。s13 可以把测试命令交给后台线程执行，先返回一个编号，例如 `bg_0001`。Agent 随后可以继续读配置文件，不必等测试结束。

这里的“后台”不是一种新的工作内容，而是一种执行方式：**这项操作现在开始，先不要挡住当前流程。**

但如果你说“明天早上 9 点再运行测试”，s13 并没有专门的机制来记录这个约定、检查时间、到点发起一轮新的模型请求。

模型在回答里说“好的，明天会检查”，不等于 Python 程序真的设置了定时任务。

### s14 解决的是：工作还没开始，谁在未来发起它？

| 需求 | 主要需要什么 | 原因 |
|---|---|---|
| 现在读一个小文件 | 普通工具调用 | 直接执行就行 |
| 现在开始一个很慢的测试，同时继续读文件 | s13 后台任务 | 解决等待慢操作的问题 |
| 每天 9 点开始检查 | s14 定时调度 | 解决未来何时发起的问题 |
| 每天 9 点开始一个很慢的检查 | s14 + s13 | 先按时间发起，再决定是否后台执行 |

所以不是“s13 做得不够好，要换掉它”。这两章回答的是两个不同的问题：

- s13：**已经要做的事，怎样执行才不挡住后面的工作？**
- s14：**还没开始的事，什么时候该交给 Agent 做？**

如果你的工具只在用户提问时工作，没有定时需求，就不必引入 s14。

### 再纠正一个容易误会的地方

s13 并不是每调用一次工具，都要用户再说一句话。一次用户请求就能让 Agent 连续调用很多工具。

它的限制在于：当 `agent_loop` 已经返回、主线程停在 `input()` 等你输入时，没有独立机制因“时间到了”而重新调用 `agent_loop`。

当前 s13 的后台结果也可能在这时完成，但“把结果写进字典”不会自动替用户按回车。s14 新增的自动交付机制针对的是定时请求，并没有顺便解决所有后台完成通知的自动唤起问题。

## 2. 先弄清楚：本章有三种不同的“任务”

同一个词被用在不同地方，是这几章难读的重要原因。

| 名称 | 可以把它理解成什么 | 它本身会运行命令吗？ |
|---|---|---|
| s12 的 `Task`，编号像 `task_...` | 工作清单中的一条记录，例如“补充测试” | 不会，主要记录状态、负责人和依赖关系 |
| s13 的后台任务，编号像 `bg_0001` | 已经交给后台执行的一次工具操作 | 对应实际的工具执行 |
| s14 的 `CronJob`，编号像 `cron_123456` | 一条定时规则：“什么时间，把什么要求交给 Agent” | 不会直接执行，它到点后产生一条请求 |

它们也不是 `asyncio.create_task()` 返回的那种 `Task`。名字相似，不代表是同一个类或同一套机制。

本章用的是 `threading` 线程，没有用 `async/await` 协程。

例如，一个 `CronJob` 可以每天触发一次。每次触发后，模型可能调用一个后台测试命令，产生一个新的 `bg_...`。模型也可以另外使用 s12 的工具记录工作，但这些编号不会被代码自动关联起来。

## 3. 从“每天 9 点检查测试”走完一遍

### 第一步：用户说出要求，模型请求设置规则

模型可以调用新工具 `schedule_cron`，传入类似下面的参数：

```json
{
  "cron": "0 9 * * *",
  "prompt": "检查项目的测试结果并告诉我结论",
  "recurring": true,
  "durable": true
}
```

先只记住：`cron` 表示时间，`prompt` 表示到点后要交给 Agent 的话。后面再拆解具体语法。

工具调用会经过 `run_schedule_cron()`，再进入 `schedule_job()`。Python 检查时间格式，创建一个 `CronJob`，放进 `scheduled_jobs` 字典。

如果 `durable=True`，它还会把规则写进 `.scheduled_tasks.json`。

到这里，完成的是“登记规则”，不是“测试已经运行”。模型是否真的调用了工具，要看工具记录，不能只看它口头答应了什么。

### 第二步：Python 检查时间，不需要一直问模型

`cron_scheduler_loop()` 在一个独立线程中运行，每隔约 1 秒看看现在几点。

它做的是普通 Python 判断：当前时间是否符合这条规则？没有必要每秒发一次模型请求问“现在该做了吗”。

因此，这种检查本身不消耗模型 token；真正请求模型时才涉及模型调用。

### 第三步：到点后，把请求放进等待列表

时间符合规则后，代码执行：

```python
cron_queue.append(job)
```

`cron_queue` 是“已经到点、等待交给 Agent 的请求列表”。

此时只表示“该处理这件事了”。还没有调用模型，更没有运行测试命令。

### 第四步：确认 Agent 能接收，再启动处理

`queue_processor_loop()` 在另一个线程中运行，每隔约 0.2 秒检查：

1. 等待列表里有没有请求？
2. 现在是否已经有一轮 Agent 在运行？

如果有请求，而且没有别的 Agent 轮次占用执行权，它就调用 `run_agent_turn_locked()`，进而进入 `agent_loop()`。

这一步解释了为什么你不再输入任何话，程序仍然能发起一轮新的处理。

### 第五步：把请求加入聊天历史，然后才调用模型

`agent_loop()` 每次进入内部循环时，会取出当前所有已到点的请求，并追加消息：

```python
messages.append({
    "role": "user",
    "content": "[Scheduled] 检查项目的测试结果并告诉我结论",
})
```

这就是 README 说的“注入消息”：**往 Python 的消息列表里追加一条记录，然后在下一次 API 请求中发送。**

`[Scheduled]` 只是一个文字标记，不会自动执行任何操作。这里使用 `user` 角色，也不代表真人又输入了一句话。

模型看到请求后，才决定读哪些文件、调用什么工具。需要执行命令时，还是原来的工具执行流程；如果命令较慢，还可能走 s13 的后台执行路径。

因此，“定时触发”不保证模型一定按预期完成工作。登记成功、到点入队、请求发出、工具成功、结果正确，是不同的阶段。

## 4. 为什么要拆成调度器、队列、处理器、Agent？

原 README 的“四层模型”，可以先翻译成下面四个问题。

| 原术语 | 通俗说法 | 代码位置 | 为什么需要它 |
|---|---|---|---|
| Scheduler，调度器 | 现在是不是该做了？ | `cron_scheduler_loop()` 调用 `check_scheduled_jobs()` | 把看时间这件事独立出来 |
| Queue，队列 | 已经到点、还没交付的请求暂存在哪里？ | `cron_queue` | Agent 忙时，请求先留下来 |
| Queue Processor，队列处理器 | 现在能不能把积压请求交给 Agent？ | `queue_processor_loop()` 调用 `process_queued_jobs()` | 即使用户不再输入，也有人负责启动处理 |
| Consumer，消费者 | 谁取走请求并处理？ | `agent_loop()` | 把请求送给模型，走原有工具循环 |

“生产者”就是把请求放进去的一方，这里是调度线程。“消费者”就是把请求取走的一方，这里是 Agent 循环。它们不是特别的 Python 类型，只是职责名称。

“调度与执行解耦”也没有那么神秘：**检查时间的代码不用等命令执行完，执行工作的代码也不用负责盯着时间。**

### 为什么不在调度线程里直接调用 Agent？

如果模型请求或工具执行耗时 30 秒，调度线程就会被这次执行挡住，没法继续及时检查其他规则。

所以调度线程只负责快速登记“这件事到点了”，然后继续检查时间。

### 为什么只有队列还不够？

队列只是数据。给列表追加一个元素，不会自动让任何函数运行。

如果没有队列处理器，而主线程又在 `input()` 等用户输入，请求可能一直留在列表里。这就是新增 `queue_processor_loop()` 的原因。

### 四层是不是四个线程？

不是。队列是一份列表，不是线程；`agent_loop()` 是函数，也不自带一个线程。

当前实现通常有以下执行位置：

- 主线程：等待终端输入；用户提交请求后，也会在这里运行一轮 Agent。
- 调度线程：反复检查时间，到点入队。
- 队列处理线程：检查积压请求；拿到执行权后，在这个线程里运行一轮 Agent。
- 另外的后台工作线程：只有工具被安排到后台时才创建，沿用 s13 的做法。

`agent_loop()` 可以由主线程调用，也可以由队列处理线程调用，但两者不能同时运行它。这就是下一节 `agent_lock` 的作用。

## 5. 几份名字相似的数据，分别保存什么？

| 变量或文件 | 保存的内容 | 例子 | 关闭程序后还在吗？ |
|---|---|---|---|
| `scheduled_jobs` | 已登记、以后还要检查的规则 | 每天 9 点检查测试 | 内存本身不在；其中 durable 规则可从文件恢复 |
| `cron_queue` | 已经到点、尚未取走的请求 | 今天 9 点这次检查 | 不在，没有写磁盘 |
| `_last_fired` | 每条规则最近在哪一分钟入过队 | `cron_123456` 在 `2026-11-03 09:00` 触发过 | 不在 |
| `session_history` | 当前会话发给模型的历史消息 | 用户提问、定时请求、工具结果 | 本章没有把它持久化 |
| `.scheduled_tasks.json` | durable 规则的定义 | 时间表达式和 prompt 等字段 | 文件保留 |

“内存”就是这个正在运行的 Python 进程临时保管的数据；“持久化”就是把需要留下来的内容写到磁盘文件中。

`CronJob` 用 `@dataclass` 定义，可以把它理解成一张有固定栏目的表格。Python 帮它生成初始化方法，所以可以写 `CronJob(id=..., cron=..., ...)`，不必自己写一堆赋值语句。

`asdict(job)` 把这张表格变成普通字典，方便转换成 JSON 文本存文件；`CronJob(**j)` 则把读取出来的字典按字段名填回对象。`**j` 在这里是“把字典中的键值作为函数参数传入”。

### 取走队列时，为什么先复制再清空？

当前实现是：

```python
with cron_lock:
    fired = list(cron_queue)
    cron_queue.clear()
return fired
```

`fired` 是这一批要处理的请求。清空共享列表后，下一次就不会再取到同一批。

复制和清空必须在同一次加锁期间完成。否则，如果别的线程恰好在“复制之后、清空之前”追加一条新请求，新请求可能被清空，却没有被复制走。

这里一次拿走全部积压请求，再逐条加入同一份聊天历史，并不是为每个请求自动创建一个独立 Agent。模型会在同一次请求中看到这一批消息。

## 6. 三把锁：分别不让谁同时做什么？

先记住“锁”的含义：同一把锁，同一时刻只允许一个线程持有。其他线程需要按相同约定拿锁，才能访问它保护的数据或执行它保护的流程。

**锁不会自动保护整个程序，也不会让某个字典变成永远安全的数据结构。** 没有拿这把锁的代码，仍然可以访问变量。

这里都是 `threading.Lock()`，用于同一进程里的线程协调，不是保护不同 Python 进程的“进程锁”。

### 6.1 `cron_lock`：保护定时规则和等待列表

调度线程要读取规则、往队列追加请求；Agent 也可能通过工具新增、取消规则，或者取走队列。

这些操作会碰到同一份数据，因此用 `cron_lock` 协调。常见写法是：

```python
with cron_lock:
    cron_queue.append(job)
```

进入 `with` 时先拿锁；离开时自动释放，即使中间抛出异常也会释放。

它通常只包住一小段共享数据操作，不应该为了等模型回复而一直占着，否则调度器也可能拿不到锁。

### 6.2 `agent_lock`：保证同一份聊天历史不会被两轮 Agent 同时处理

假设你刚提交一个问题，恰好定时任务也到点了。如果两个线程同时向 `session_history` 追加消息、发送模型请求、追加工具结果，历史可能交错，工具调用和结果也可能对不上。

所以双方必须先拿同一把 `agent_lock`，拿到的一方才可以运行完整的一轮 Agent。

主线程的写法：

```python
with agent_lock:
    run_agent_turn_locked(query)
```

如果锁被占用，主线程会在这里等。注意 `input()` 在这个 `with` 外面，所以你在终端慢慢打字时，不会一直占着锁阻止定时任务。

队列处理器调用的 `process_queued_jobs()` 中这样写：

```python
if not agent_lock.acquire(blocking=False):
    return False
```

把这一句翻译成白话：

> 尝试拿锁。如果现在有人占着，就不要停在这里等，先跳过这次检查，下轮再试。

`acquire` 是拿锁；`blocking=False` 是拿不到就立即返回 `False`。`process_queued_jobs()` 也随即返回，表示这次没交付。外层的 `queue_processor_loop()` 稍后会再次调用它；每次检查前还有 `time.sleep(0.2)`，并不是一直高速空转。

拿到锁以后，处理器还会再检查一次队列。因为从第一次检查到拿锁之间，原来正在运行的 Agent 可能已经把请求取走了。

用 `acquire()` 手动拿锁，就要配套释放：

```python
try:
    run_agent_turn_locked()
finally:
    agent_lock.release()
```

`finally` 表示不论正常结束还是中途抛异常，都要执行释放动作。否则锁可能一直被占着，之后谁都进不来。

函数名里的 `_locked` 只是提醒调用者“你调用前应该已经拿锁”。这个名字本身没有任何自动加锁的魔法。

### 6.3 `background_lock`：保护后台操作的状态和结果

这是 s13 已经有的锁。后台线程写“命令完成了”，Agent 读取“有哪些结果可以收集”，两边要协调。

它和前两把锁保护的不是同一件事。

尤其要注意：**`agent_lock` 只串行化 Agent 轮次，不会等待所有后台命令结束。** 一轮 Agent 结束时，后台测试仍可能在跑；后来的定时请求也可能启动另一份测试。本章没有自动防止同一个后台命令重叠执行。

### 这些锁能保护磁盘文件吗？

不能把这句话理解成“已经有完整文件安全保证”。当前新增、取消、删除一次性规则时，都在 `cron_lock` 内保存文件，可以避免本进程中的这些保存操作同时发生。但是仍没有临时文件替换、跨进程文件锁等机制，写到一半退出仍可能损坏文件。

`save_durable_jobs()` 要求调用者先拿锁，函数内部不会再拿一次。同一线程拿着普通 `Lock` 再获取同一把锁，会停在那里等自己释放，形成死锁。

所以本章只展示基本协调思路。若同时启动两个 s14 进程，它们各有自己的锁，不能相互排斥，还可能同时触发同一条规则或覆盖文件。

## 7. Cron 表达式：用五栏表示什么时候做

`cron` 原本是 Unix 系统中定时执行任务的机制名称。本章没有把任务安装到系统 cron，而是用 Python 自己检查一种类似的时间表达式。

五栏依次是：

```text
分钟    小时    一个月中的第几天    月份    星期几
 0       9             *            *         *
```

这一行的意思是：月份、日期、星期都不限，但小时必须是 9，分钟必须是 0。

| 写法 | 通俗含义 | 示例 |
|---|---|---|
| `*` | 这一栏不限制 | 小时栏填 `*`，表示每个小时都可以 |
| `N` | 必须等于这个数字 | 小时栏填 `9`，表示 9 点 |
| `N-M` | 在这段范围内，包含两端 | 星期栏填 `1-5`，表示周一到周五 |
| `N,M` | 是列出的数字之一 | 小时栏填 `9,18`，表示 9 点或 18 点 |
| `*/N` | 本 demo 检查当前值能否被 N 整除 | 分钟栏填 `*/5`，匹配 0、5、10 等分钟 |

完整例子：

| 表达式 | 什么时候匹配 |
|---|---|
| `* * * * *` | 每一分钟 |
| `*/5 * * * *` | 每小时的 00、05、10、15 等分钟 |
| `0 9 * * *` | 每天 09:00 |
| `0 9 * * 1-5` | 周一到周五的 09:00 |
| `30 9,18 * * *` | 每天 09:30 和 18:30 |

### “每五分钟”不等于“创建之后再过五分钟”

如果 09:03 设置 `*/5 * * * *`，下一次匹配是 09:05，不是 09:08。

它是在匹配钟表上的刻度，不是在累计任务创建后经过了多久。

而且没有“秒”这一栏。若 09:05:20 创建规则，调度器在 09:05:21 检查时仍可能发现当前分钟匹配，马上触发。不能把它当成精确延时接口。

### DOM、DOW 是什么？

- DOM：day of month，一个月里的第几天，例如 1 号、15 号。
- DOW：day of week，星期几。

本代码的星期编号是周日 `0`、周一 `1`，一直到周六 `6`。Python 的 `weekday()` 则把周一编号为 `0`，所以代码用 `(dt.weekday() + 1) % 7` 做转换。

当日期和星期都写了限制时，本实现采用“满足任意一个即可”：

```text
0 9 1 * 1
```

意思是：每月 1 号的 9 点，或者每周一的 9 点。不是“只有 1 号恰好是周一才执行”。

但分钟、小时、月份仍然要同时满足。

### 这个解析器并不等于完整的 cron 产品

它只支持代码中实现的简化语法。例如 `1-10/2`、`MON`、用 `7` 表示星期日，都不是本章支持的写法。

`*/N` 的实现是直接计算 `value % N == 0`，在日期、月份这种从 1 开始的字段中，不能假设它与其他 cron 实现的步长起点完全相同。

代码用 `datetime.now()`，采用运行进程的本地时间，没有为每个任务设置时区。涉及跨时区、夏令时变化时，要另外设计，不能直接拿这个 demo 作精确时间保证。

## 8. 为什么每秒检查，却不会一分钟执行几十遍？

规则 `0 9 * * *` 在 09:00:01、09:00:02、09:00:03 都匹配，因为表达式只看到“小时 9、分钟 0”。

如果只判断匹配就入队，这一分钟会重复产生很多请求。

因此代码额外保存：

```python
_last_fired[job.id] = "2026-11-03 09:00"
```

下一秒再检查时，发现这个任务已经在这一分钟触发过，就不重复入队。

`minute_marker` 就是这种“精确到分钟的时间标记”。里面包含年月日，是为了区分今天 09:00 和明天 09:00。

这叫“去重”：尽量避免把同一次触发重复登记。但它只在当前进程的内存里有效，重启后记录就没有了。同一分钟重启，仍可能再次触发。

代码把“反复检查”和“检查一次”分开了：`cron_scheduler_loop()` 负责循环与等待，`check_scheduled_jobs()` 负责判断和入队。其他细节可以逐句翻译：

- `while True`：一直重复做检查，直到进程结束或线程因未处理的错误停止。
- `time.sleep(1)`：只暂停这个调度线程约 1 秒，不是让整个程序都停下来。
- `list(scheduled_jobs.values())`：先拿到一份当前规则列表，因为后面可能删除一次性规则，不能边遍历原字典边改变它的大小。
- 每条规则内部的 `try/except`：某条规则处理出错时，打印错误并继续处理其他规则，而不是因此结束整个调度线程。

“轮询”就是这样隔一段时间主动检查一次。它好理解，但不是精确闹钟：系统忙、进程被暂停、Agent 忙，都可能使实际处理晚于预期。

## 9. recurring 和 durable：两个互不替代的开关

`recurring` 问的是：这条规则触发一次以后，还要继续保留、等待下次触发吗？

`durable` 问的是：要不要把规则写进文件，让下一次启动还能恢复？

| recurring | durable | 含义 |
|---|---|---|
| `True` | `True` | 重复规则，并写文件 |
| `True` | `False` | 重复规则，但只在本次运行期间保留 |
| `False` | `True` | 只触发一次；尚未触发时可从文件恢复 |
| `False` | `False` | 只触发一次，而且只在本次运行期间保留 |

`one-shot` 就是只触发一次；`session-only` 就是只在当前会话或当前这次程序运行期间存在。

### 一次性任务不是“执行成功后才删除”

当前代码在匹配时间、放入 `cron_queue` 后，就从 `scheduled_jobs` 删除一次性规则；若需要持久化，也会更新文件。

这时 Agent 可能还没处理它。如果随后进程崩溃，等待队列丢失，规则又已经删除，这次工作就可能丢掉。

因此 `recurring=False` 的真实含义是“只入队一次”，不是“保证成功一次”。

它也不天然表示“从现在起一分钟后”。如果使用 `* * * * *`，可能下一秒就在当前分钟触发。五栏表达式没有年份，不能直接完整表达某个带年份的唯一时间点。

### durable 不等于程序关闭后仍会工作

本章的调度器就在这个 Python 进程里。进程关闭，检查时间的线程也停止；磁盘上的 JSON 不会自己运行。

下次启动，`load_durable_jobs()` 读回的是规则，而不是一份“关闭期间错过了哪些执行”的记录。

例如每天 09:00 的规则，程序 08:00 关闭，10:00 重启：当前时间不是 09:00，代码不会自动补跑今天错过的那一次。

这比“重启就恢复任务”更准确：**恢复的是未来继续检查的规则，不是保证补回过去的工作。**

### daemon=True 是什么意思？

这里可以理解为：“主程序结束时，不要因为这个线程还在循环，就一直阻止进程退出。”

它不是“程序关掉了也能活着的后台服务”，也不保证退出前会把未完成工作处理完或保存好。

如果希望应用关闭后仍能定时启动任务，需要另一个持续运行的服务，或操作系统提供的定时机制；保存 JSON 本身做不到这一点。

## 10. Agent 已经很忙时，定时请求会怎样？

分两种情况理解，比一句“空闲时执行”更准确。

### 情况一：当前 Agent 还会继续自己的工具循环

请求先进入队列。当前 `agent_loop()` 下一次走到 `while` 顶部时，就会取走请求、加入历史，下一次调用模型时一起发送。

这不需要队列处理器另开一轮，因为已经有一轮 Agent 在运行。

它也不能打断正在进行的模型请求或工具函数，只能等程序走到这个检查位置。

### 情况二：当前 Agent 已经结束，或马上结束

请求暂时留在队列里。锁释放后，队列处理器可以拿到锁，调用 `run_agent_turn_locked()` 开始处理。

所以 `agent_lock` 在这里表达的“空闲”，主要是“当前没有别的 Agent 轮次持有这把锁”，不是“机器没有其他事情在做”。

### 很多规则一起到点怎么办？

本章会把请求都放进列表，取出时全部加入同一份历史。没有优先级、数量上限，也没有“同一种请求已经积压了就合并”的机制。

如果处理速度赶不上触发速度，就可能积压很多请求。这里的“积压”只是：新请求产生得比旧请求处理得快，等待列表越来越长。

### 取消规则会停止已排队或正在执行的工作吗？

不会。`cancel_job()` 删除的是 `scheduled_jobs` 中的规则，防止以后继续按它触发。

已经在 `cron_queue` 里的请求不会因此被移除；正在进行的模型调用和后台命令也不会因此停止。

“取消未来安排”和“停止当前执行”是两种不同操作，本章只实现了前一种。

## 11. 按什么顺序读代码，不容易迷路？

建议先跳过文件前半部分的任务系统、普通工具、提示词组装，直接搜索下面这些名字：

1. `CronJob`：先看一条规则保存什么。
2. `scheduled_jobs`、`cron_queue`、`_last_fired`：区分规则、已到点请求、去重记录。
3. `schedule_job`：看规则怎样被登记；`run_schedule_cron` 只是工具包装。
4. `check_scheduled_jobs`，再看 `cron_scheduler_loop`：先理解一次检查怎样入队，再理解如何不断检查。
5. `process_queued_jobs`，再看 `queue_processor_loop`：先理解一次交付，再理解为什么不用等用户再次输入。
6. `run_agent_turn_locked`：看用户请求和定时请求怎样共用同一份历史。
7. `agent_loop` 顶部的 `inject_scheduled_requests`，再看它调用的 `consume_cron_queue`：看请求怎样变成模型真正看到的消息。
8. 最后再看 `cron_matches`、`validate_cron` 和文件读写，补上时间格式与保存细节。

`validate_cron()` 只负责先检查格式、数值范围，避免把明显坏的规则注册进去；`cron_matches()` 才负责判断“这个时间是否符合规则”。检查规则是否合法，与判断现在是否到点，是两件事。

当前代码把 `load_durable_jobs()` 和两个长期循环线程的启动都放在了 `if __name__ == "__main__"` 里面。直接运行脚本才会恢复规则、启动调度，`import` 不会自动启动这些线程。

但 `import` 仍会执行顶部的环境读取、客户端初始化和任务目录创建，不能理解成完全没有初始化动作。拆出的 `check_scheduled_jobs(now)` 可以传入固定时间检查规则，不必真等到第二天；`process_queued_jobs()` 则只尝试交付一次，便于单独理解与测试。

## 12. 怎样观察这个 demo？

当前 s14 与 s01-s13 一样使用 OpenAI SDK 的 Chat Completions 接口，从 `.env` 读取 `LLM_API_KEY`、`LLM_BASE_URL`、`LLM_MODEL_ID`。设置 DeepSeek 对应的地址和模型名，就会请求 DeepSeek，不是因为使用 OpenAI SDK 就固定调用 OpenAI 模型。

工具协议也沿用前章：保存模型的 `assistant.tool_calls`，再为每条调用追加带原 `tool_call_id` 的 `role="tool"` 回复。这一批回复完成以后，才追加定时请求或后台通知，避免把工具配对拆开。格式可对照 [OpenAI 官方接口文档](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)。

若已经为当前 s14 配好运行环境，可以从项目根目录运行：

```sh
python s14_cron_scheduler/code.py
```

模型调用可能产生费用。先在无敏感数据的练习目录使用只读命令，不要一上来设置自动部署、删除或写入任务。

可以让模型设置一个本次会话有效、每分钟触发的简单请求，例如：

> 设置一个定时规则：每分钟运行 date 命令并告诉我结果。recurring=true，durable=false。请确认已经调用 schedule_cron，并返回规则编号。

`date` 只是读取时间。由于匹配的是当前分钟，它可能很快第一次触发，不必等满 60 秒。

然后观察这几个标记：

| 标记 | 到了哪一步 | 还不能据此说明什么 |
|---|---|---|
| `[cron register]` | 规则已登记 | 不代表工作已执行 |
| `[cron fire]` | 时间匹配，请求已入队 | 不代表模型已经收到 |
| `[queue processor]` | 空闲时启动自动交付 | 已运行的 Agent 自己取队列时，不一定出现这个标记 |
| `[inject cron]` | 请求被加入消息列表 | 不代表 API 调用或命令一定成功 |
| `> bash` 及后续结果 | 模型请求了命令工具，程序开始处理 | 仍要看具体结果，不能仅凭工具名称判定成功 |

完成观察后，用 `cancel_cron` 取消规则，再用 `list_crons` 确认不再列出。取消前已排队的请求仍可能执行，原因见第 10 节。

`.scheduled_tasks.json` 是相对于启动时的工作目录保存的，因为代码用的是 `Path.cwd()`。从项目根目录启动，它就在根目录，不是在 s14 子目录。

如果只想先验证机制，不想消耗模型费用，可以运行离线测试：

```sh
python -m unittest discover -s tests -p 'test_s14_cron_scheduler.py' -v
```

测试使用临时目录、假的凭据和模拟的 API 回复，不读取真实 `.env`，不改项目的规则文件，也不会启动长期运行的调度线程。它验证程序如何处理结果，不等于验证了真实服务端的响应。

## 13. 教学版到这里就够了，但哪些保证还没有？

学本章时，不必把这些功能一起实现。但设计真正长期运行的系统时，需要知道缺在哪里。

| 问题 | 当前 demo 的情况 | 为什么实际使用时要考虑 |
|---|---|---|
| 应用关闭时仍要执行 | 做不到 | 调度线程随着进程停止 |
| 关闭期间错过的任务 | 不自动补跑 | 没有记录并重放错过的触发 |
| 请求丢失 | 可能发生 | 队列只在内存里，取出后也没有成功确认再删除的机制 |
| 重复执行 | 可能发生 | 去重记录不持久化，多进程也没有协调 |
| 任务执行失败 | 没有完整恢复流程 | 本章没有接入 s11 的完整错误恢复，也没有失败后重新入队策略 |
| 同一后台任务重叠 | 没有统一限制 | Agent 轮次结束，不代表后台命令已经结束 |
| 规则文件可靠保存 | 只有简单 JSON 读写 | 并发写入、写到一半退出、损坏文件都需要额外处理 |
| 权限与安全 | 不因“到点”而自动安全 | 定时运行命令仍需要权限边界，bash 并没有因为 safe_path 就被全面隔离 |
| 终端交互体验 | 输出可能打断正在输入的文字 | 输入线程和自动执行线程共用终端，没有专门 UI 协调 |

两个后面经常会遇到的词，也先用具体例子记住：

- **确认收到或完成，acknowledgement**：消费者明确告诉系统“这次请求已经处理好”，系统再删除记录。本章取出队列时就清空了，没有这样的确认流程。
- **幂等，idempotency**：同一请求意外执行两次，也不会造成重复的额外影响。例如同一订单的“发送一次提醒”不能因为重试发出两封邮件，需要用请求编号记录是否已经处理。本章的分钟去重不等于整个业务已经幂等。

原 README 最后的“深入 CC 源码”是另一份实现的分析，不是本章 Python 已经拥有的功能，也不应直接当成某个产品当前版本的保证。先理解本章，不需要先背那些内部文件名和配置项。

其中几个词的意思是：

| 术语 | 通俗含义 |
|---|---|
| 文件锁 | 用跨进程的协调方式，避免两个程序同时处理同一份共享状态；不同于这里的 threading.Lock |
| 文件观察者 | 监视文件是否被修改，修改后通知程序重新读取 |
| 优先级 | 多条请求等待时，决定谁先处理 |
| 抖动，jitter | 把很多同时触发的工作稍微错开，避免全部挤在一个时间点 |
| 惊群 | 一批等待者同时被唤醒或发起请求，瞬间争抢资源 |
| 自动过期 | 一条规则到期后不再继续触发，避免无限保留 |
| 功能开关、feature flag | 决定某项功能是否向用户开放的配置 |
| QoS | 服务质量或资源待遇；例如资源紧张时，交互请求和定时请求可能采用不同调度策略 |

这些都是可以在基本链路成立后再增加的机制，不是理解 s14 的前提。

## 最后只记住这四句话

1. **s13 决定已经开始的慢操作怎样执行；s14 决定未来何时发起工作。**
2. **调度器只判断时间并入队，模型和工具仍负责实际工作。**
3. **队列存请求，处理器启动交付，锁避免两轮 Agent 把同一份历史同时改乱。**
4. **保存规则不等于保存待执行请求，更不等于保证准时、成功、只执行一次。**
